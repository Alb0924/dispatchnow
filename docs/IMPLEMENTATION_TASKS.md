# DispatchNow 任务拆分与实施顺序

设计依据为开发文档 v1.0。最终架构保持模块化单体，只有 dispatchnow-app 是启动应用。按下表逐步开发，每次交付源码、简明说明和验收结果，再进入下一个任务。

## 核心开发步骤

| 步骤 | 对应里程碑 | 实现内容 | 验收条件 | 当前状态 |
|---|---|---|---|---|
| 01 | M1 | 根 POM、app 与四个业务模块、Wrapper、启动配置 | JDK 21 构建成功，实际 HTTP 健康检查通过 | 已完成 |
| 02 | M1 | Windows 后端连接既有 VM 三项服务，保留可选同机 Compose | 用户原自检已连通；修复版完成隔离协议联调和探针检查 | 已完成 |
| 03 | M1 | 核对既有 46 表、Flyway 显式基线接管、MyBatis 基础 | 现有库保留；空库 V1、接管库与后续 V2 均可验证 | 进行中 |
| 04 | M1 | 统一响应、业务错误、参数校验、请求 traceId | 错误码和 HTTP 状态一致，响应不泄露内部异常 | 未开始 |
| 05 | M1 | 用户注册、登录、注销、角色、会话与 CSRF | 密码安全保存，注销后会话失效，修改请求受保护 | 未开始 |
| 06 | M1 | 自有地址簿、骑手资料与上线状态 | 地址越权被拒绝，骑手状态与容量归履约模块维护 | 未开始 |
| 07 | M2 | 服务区域、计费规则、QuoteService 与报价快照 | 距离重量进位、报价期限和边界测试通过 | 未开始 |
| 08 | M2 | 创建配送单、报价唯一消费、请求幂等 | 同报价或同请求并发创建只产生一张订单 | 未开始 |
| 09 | M3 | 模拟支付、回调、支付超时、退款和晚到支付 | 关闭订单不会被晚到回调重开，退款不重复 | 未开始 |
| 10 | M4 | 抢单、有效指派、派单轮次和骑手容量事务 | 多人抢一单与一人抢多单均满足约束 | 未开始 |
| 11 | M4 | 到达取件点、取件码、送达码、状态机与容量释放 | 旧骑手操作被拒绝，重复送达不二次释放容量 | 未开始 |
| 12 | M5 | 位置会话、序号、GEO、轨迹采样和 WebSocket | 旧位置不覆盖新位置，过期点不参与派单，断线能恢复 | 未开始 |
| 13 | M5 | 取件前取消、基本异常工单、原骑手退回 | 取件后通过退回流程结束，交回确认后才释放容量 | 未开始 |
| 14 | M5 | Vue 用户端、骑手端、运营端基本页面 | 能完整演示下单、抢单、取件、送达和退回 | 未开始 |
| 15 | M6 | 自动邀约、拒单、过期处理、范围扩展与到期任务领取 | 旧邀约不能接受，重复超时处理不破坏当前状态 | 未开始 |
| 16 | M7 | Outbox 补发、消费幂等、ACK、退避、死信与任务恢复 | 在提交、发送、ACK 边界中断后仍能正确收敛 | 未开始 |
| 17 | M7 | 异常分派、审计、指标、会话与多实例故障测试 | 关键异常可追踪，权限和容量检查持续成立 | 未开始 |
| 18 | M8 | 固定数据模拟、压测、策略基线、部署和演示记录 | 代码版本、配置、输入与测试结果能够对应 | 未开始 |

01 至 14 完成 P0，15 至 18 完成 P1。身份、幂等、容量约束和业务事实持久化在对应功能第一次实现时就加入；第 16 步是补全消息恢复能力，不是第一次保存订单事件。

为了让后续步骤连续，09 就保存支付、退款与到期任务记录，10 就保存状态日志和 Outbox；在 16 中补齐发送补偿、消费恢复与故障注入。用户现已按完整设计手工创建 46 张表，03 改为接管已有结构。后续变更使用新迁移，扩展表先存在不等于扩展业务已实现。

## 每一步的交付规则

每次交付包含可构建源码、本步修改与运行说明、已执行检查、实际验收结果以及下一步明确入口。状态只有“未开始”“进行中”“已完成”；没有通过验收的内容不能标记已完成。

当前主运行方式是 Windows 连接已有 VMware 虚拟机服务。用户提供过原版 2 + 5 项本机测试通过记录；本次修复版的隔离联调和范围见 VERIFICATION.md。用户 VM 的实时网络与授权没有由本次环境重新直连验证，按 README 在本机复核即可。可选 Compose 的容器运行不再作为 VM 主流程的前置条件。

第 03 步已有完整结构，但尚未接入 Flyway。下一步按 NEXT_TASKS.md 做只读核对、显式 baseline 与双路径迁移测试，再进入统一响应、认证和地址接口。架构继续保持模块化单体。
